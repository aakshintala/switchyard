---
name: ci-triage
description: "Classify a failed CI run before any retry or fix: real failure, flake, stale base, merge conflict or infrastructure. Use when CI fails on a PR, or before rerunning any CI job."
---

Failed CI is evidence. Classify it before touching code or rerunning anything. The tool is `~/.agents/bin/gh-ci` (`snapshot`, `wait`, `verdict`, `failures`, `watch-verified`, `resample`; usage at the top of the script).

### 1. Read

Read `tkt-ship`'s digest first when one exists. `gh-ci snapshot <pr> --repo <owner/name>` for the head SHA and status, then `gh-ci failures --pr <pr> --repo <owner/name>` for every failed or cancelled job on that head, each failed job with the tail of its failed-step log. Read the digest before opening any raw log, and hand it to the fix job as its evidence. For a commit with no PR (a branch tip, or `main` after a merge), `gh-ci verdict <branch-or-sha> --repo <owner/name>` judges its checks against the default branch's required checks. Its first line is `RED` (a required check failed or was cancelled), `NOT YET` (a required check is pending or missing), `NOT RED` (only non-blocking checks failed) or `GREEN`; any verdict can be followed by one `REQUIRED: <name>` or `NON-BLOCKING: <name>` line per failed or cancelled check, names only, no logs. It exits 0 for `GREEN` and `NOT RED`, 1 for `RED`, 124 for `NOT YET`, and 2 for a usage error, a ref GitHub cannot resolve, or no repo to judge (no `--repo`, `GH_CI_REPO` or GitHub origin). An API or parse error also exits 1, with a `gh-ci:` message on stderr and nothing on stdout, so an exit 1 is `RED` only when the first line says so; with no first line, rerun it. Its 124 means a required check is pending now and nothing waited, unlike `wait`'s 124, which means the wait timed out. It judges against the default branch's required checks, so for a PR use `wait <pr>`, which reads the PR's own base. A `GREEN` with `gh-ci: no checks on <sha>` on stderr means the default branch requires no checks and none ran: nothing was judged. With `NOT YET`, the same line means the required checks have not started. Never read red from a run's own conclusion: a non-blocking job turns it red while every required check passed. For a mutation-testing job the digest tails one shard: hand on every failed shard's surviving mutants from `~/.agents/bin/mutant-verdicts <run> --repo <owner/name>` once the run finishes (one line per mutant: the mutant, a tab, one of `caught`, `missed`, `timeout`, `unviable`; the `missed` and `timeout` lines are the surviving mutants), falling back to the shard log (`gh run view <id> --repo <owner/name> --log-failed | grep -E 'MISSED|TIMEOUT'`) when the run's artifacts are gone (expired). A cancelled job has no log: a newer push or run superseded it, or it hit its job timeout; check which before calling it red. A failed job with no failed step, or whose log 404s (logs can stay unavailable for a while after a failure), may carry the runner's error in its check run's annotations (`gh api repos/<owner/name>/check-runs/<job id>/annotations`; an Actions job id is its check-run id): read them before calling the job unreadable.

Done when every red leg has its failing test or step named, or its runner error when no step failed.

### 2. Classify

One class per red leg, and the one action it allows:

- **Merge conflict**: GitHub runs no CI on a conflicting PR. Rebase onto `origin/main` and resolve with `resolving-merge-conflicts`.
- **Stale base**: the failure is in code the diff never touched, and `origin/main` has moved past the merge-base. Rebase onto `origin/main`. Check this before calling anything a flake. A timeout counts too: a job whose work scales with the diff (mutation testing, affected-test selection) can time out on a PR behind `origin/main` when its diff picks up main's own commits: rebase onto `origin/main` before rerunning it. A job that fails on an unknown flag or argument on a branch behind `origin/main` counts too: a `pull_request` run takes its workflow file from the PR merged with main, but a job that checks out the PR head builds the branch's older code, which lacks the flag main added.
- **Infrastructure**: a runner, network or quota outage, or a setup step (toolchain or tool install) that fails or times out, with no test failing. Rerun the failed jobs once (`gh run rerun <run id> --failed`): no code of the PR ran, so the rerun hides nothing. When the PR changes that step itself (the toolchain, an action pin, the workflow), its code did run: classify it as real. A second infrastructure failure gets reported with the run id and head SHA; change no code.
- **Flake**: the same test passes elsewhere on the same platform, and nothing in the diff links to it. One fresh build (an empty commit), never a job retry. An identical second failure means it isn't a flake: reclassify as real. Check the failing assertion against `origin/main` first. File the flake as an issue in the `test-only` category (per `docs/agents/triage-labels.md`), never `bug`: the full test name, the head SHA, the panic line verbatim, the run link, the saved output and the suspected cause. Its PR states the root cause and carries a deterministic repro: a test or pause point that forces the failing interleaving and fails without the fix, never repeated or loaded runs.
- **Real failure**: the diff causes it. Fix it in a new commit.

`gh-ci resample` reruns a job to measure how often an intermittent failure happens. It is a diagnostic, never a way to get green.

Done when every red leg has a class, posted as a PR comment with its evidence.

### 3. Act and re-enter

Take each class's action, and push the collected fixes once, after the run ends or a job on it fails. Any commit this makes re-enters `review-loop` at its verify step, on the same counter, so the merged head is one a verdict covers. Wait with `gh-ci wait <pr> --repo <owner/name> [--timeout <s>]`, unpiped so its exit code reaches you, in the wait mode your harness instructions prescribe: it blocks until no required check on the PR's current head is pending (a required check with no run on the head counts as pending), then exits 0 when all are green, 1 printing each `failing: <name>`, 3 when the PR still has merge conflicts after about 30 s of re-checks (or once the timeout budget is spent), or 124 on timeout with checks still pending. Exit 1 with `could not read the head of PR` is a transient API error: rerun the wait. On a draft PR it ignores the required names, since they have not run, and judges only the checks on the head: green exits 0 printing `CI: pass (draft: required checks run once ready)`, a failure exits 1, and a head with no checks stays pending; run `gh pr ready <pr>` first when the wait gates a merge. Use it rather than a loop of your own over `gh-ci snapshot`.

Done when the required checks are green on the PR's current head SHA, or the failure is reported with its class, run id and SHA.
