---
name: planning
description: "Write a ticket's implementation plan: a contract sketch (rulings, files, tasks, interfaces, review focus), checked by a Verifier, posted on the ticket, and filled into the lane brief. Use when planning a ticket before a lane builds it, or filling a preflight, planner, Verifier or lane brief."
---

The orchestrator writes every ticket's plan, after reading the code it describes: a lane fails on a plan describing code its author never read. The plan becomes the body of the lane's brief.

**Briefs.** The templates are `briefs/preflight.md`, `briefs/planner.md` (for a worker that writes the plan), `briefs/verifier.md`, `briefs/confirm.md` and `briefs/lane.md`. Fill them with `~/.agents/bin/fill-brief <template> KEY=VALUE...` (a value of `@<file>` reads the file), which fails on any unfilled placeholder or unknown key (a template's keys are its `__NAME__` placeholders), so the brief never goes out half-filled and you write only the values. When a filled brief starts another job, fill it with `--out <absolute path>` (e.g. `~/.cache/agents/<repo>-<issue>-<template>.md`: a durable directory, since a reboot clears `/tmp`; `fill-brief` creates it) and use the printed line verbatim as its prompt, never a hand-written path.

**Base.** Every brief takes `BASE`, the code the plan describes, which the orchestrator prepares (see `implement` step 2): `origin/main` for a new ticket, the PR's branch with `origin/main` merged in for a re-plan. Read, plan and verify against that base.

**Pack.** `plan-sweep` writes the ticket's context pack: symbol sites, file outlines, doc sections, and an Outside Files list of the paths its symbols reach that the plan's Files do not cover. `preflight.md`, `planner.md`, `verifier.md` and `confirm.md` take it as `PACK` (`none` when no sweep ran). With a state file, `tkt-start` writes it and `tkt-plan <state> set` rewrites it from the plan; by hand, `~/.agents/bin/plan-sweep --help` shows the call.

**Commands.** With a state file, steps 2 to 5 run through `tkt-plan` and `tkt-build`, started as `implement`'s Commands says; each step below names what its command does. Without state, the step's own text is the procedure.

### 1. Read

Start from the pack and read further code only where it points. Read every file the preflight listed and every file the plan will name. Line numbers in a ticket or brief are hints: anchor each citation by grep or heading at the base. Send bulk reading beyond that (history, issue archives, unrelated modules) to sub-agents that return summaries.

Read every ruling posted on the ticket. A plan that touches a mechanism a posted ruling governs, a re-base re-plan included, quotes that ruling under Rulings and follows its words.

Done when you have read every file the preflight listed, every file the plan will cite and every ruling posted on the ticket.

### 2. Write the plan

A plan is a sketch of contracts and invariants, never code: a function body in a plan is the implementation done twice.

```
# Plan: #<n> <title>
<one-line goal>
Base: <full SHA of the base the plan was read against>

## Project constraints  pointers to the repo's standing rules (dependencies, budgets, code rules) where the workflow doc lists them; never copied
## Rules this ticket implements  each governing sentence from a doc, spec or ticket, quoted word for word with its file and section
## Rulings              each contradiction found and the default chosen, tagged core or non-blocking
## Files                only the paths the lane writes, each with what changes; this is the lane's fence, and tools read every path listed here as held. Sweep for it, ruling each hit in or out from its lines in the file, never from a summary: start from the pack's Outside Files list, then search the repo for every changed symbol, signature, type, listed value and behaviour, and list every caller, test, rules or lint file, doc and dependency manifest the change reaches: the tests and snapshots pinning output or a list the change shifts or extends, every exhaustive match on an enum gaining a variant (found by adding the variant in a scratch copy of the base and building every target, since a name search misses a match on a field of that type, such as `match failure.code`; list each file the build reports), every use of a deleted or renamed type, every test file that calls a changed or removed name, the file a `#[path]`-declared test module lives in (the declaring file is not it), and the lockfile for a new dependency. A caller count in the plan quotes the search that produced it. Write each path in backticks, since `plan-check` reads only backticked tokens; a directory ending in `/` or a pattern holding `*` covers the paths under it
## Tasks                in order; each: behaviour, test first, gate command, done-when
## Gate                 the lane's gate as one literal command line: format, lint and tests for every package Files touches, each run through the runner the workflow doc names (e.g. `cargo nextest run`, not `cargo test`, when it names nextest), plus the checks the workflow doc requires before a push; the section holds only that line, since `plan-gate` reads all of it: join the steps with `&&`, write `$(…)` for a substitution (`plan-gate` fails a backtick left after it strips the wrapping pair), and put a note on the gate under Rulings
## Red commit           when the workflow doc gates `bug` fixes on a commit that fails first: the test files that commit holds alone (they must build without the fix); otherwise `none`
## Interfaces           signatures, invariants, one literal example per line on the wire; no bodies. Each existing hook, seam or helper a task or test relies on, with its file, function and visibility (e.g. `pub(crate)`)
## Review Focus         where reviewers look: input classes and failure modes the tests may not cover
## Rung                 the lane's rung (per the `delegate` skill) and the reason
## Size                 estimated lines of code and lines of tests, separately; the split, if any
```

The quoted rules are what the Verifier, the reviews and any finding are judged against: a finding that contradicts a quoted rule is refuted by quoting it. A rule you can't quote from its doc is dropped, or asked of triage. A field or shape on an external wire cites its research file or probe output under Interfaces; one with neither is a `core` ruling. Check each ruling before the Verifier does: a ruling on behaviour a doc governs names the quoted rule it follows, and one that promises runtime behaviour cites the code at the base that runs it.

A hazard you know of is settled in the plan: a ruling (what the code does about it), or an invariant under Interfaces, which the Verifier attacks and the lane keeps. Review Focus holds only places to look. A hazard you can't rule on is a `core` ruling, and parks the ticket. So is a ruling that contradicts a ticket criterion or a doc sentence, or that invents behaviour a person or a calling model sees (a tool result, a message field) where the doc is silent: the ticket and the docs belong to whoever triages them, so such a ruling parks the ticket before the Verifier runs and never ships in a plan. A choice between two readings of a doc sentence is a `core` ruling too, never a `non-blocking` default. The plan carries every behaviour the ticket states: none is deferred to another ticket or part, and a ticket too big for one plan is split.

The rung is `standard` by default. It is `strong` when Interfaces or Review Focus involve state carried across calls, concurrency or timing, replay, or a quoted rule with several cases, and `frontier` for cross-cutting design.

Estimate tests from the testing rules the workflow doc states (every case, every listed sequence), never as a fraction of the code: plans have come in at half their merged size, mostly in tests. Count a built change's lines, sites and asserts against `git merge-base origin/main HEAD`, which leaves out main's newer commits. When the workflow doc's size rule calls for a split (past 1,800 lines of code plus tests only when the doc says nothing about size), split the ticket into parts from the start: each part a lane and PR of its own, in order, cut at a seam that leaves main green, `Part of #<n>` until the last, which is `Resolves #<n>`. A plan near GitHub's 65 KB comment limit means the ticket needs a split: triage adds Delivery parts to the ticket body, and each part gets its own plan.

A ticket that adds a ban (a lint, a disallowed method, a grep check) lands the ban in its first PR, with every existing site allowed by name, so no new site arrives while the migration runs; later PRs remove the allowances. A mechanical migration (one rewrite applied at every site, with no behaviour change) is one PR whatever its size: its review reads one rewrite, however many sites it touches.

Size each task as the smallest unit that carries its own test cycle. A regression test for a race names the mechanism that forces the interleaving (a pause point, barrier or held lock) and is checked to fail without the fix before dispatch; a test that only runs the path passes either way. A task that changes a threshold or adds a guard names the assertion that kills its obvious mutant: the value held at the boundary, both sides of it, or the exact error kind, never only "tests pass"; CI's mutation run catches the gap otherwise, one round late. Tasks run in order in one lane, under one `review-loop` for the PR. A migration may break the callers it lists under Rulings instead of paying for interim compatibility. A task that rewrites a literal across files names a script run on a scratch copy and checked by diff, or edits by hand. A script's check that a file contains X runs before the insertion it guards; after it, the check always passes.

A task with a wait, poll or retry carries a margin table: per wait, the margin is the bound minus the time of the event it waits for, in ms, computed from the code's constants (quote them) in one pass over every wait the change touches, so a Verifier round checks the table and finds no further row. A fake clock advanced on a "parked" state names the thread and the signal that the awaited state was recorded.

Defaults come from the project's catalogues first: an error code from the error doc, a name or format from the doc that lists it. A fence grant for a shared file names the line. A type from another crate is written in the path form that resolves (`::tools::` when the crate has its own `mod tools`).

With a state file, record the plan with `tkt-plan <state> set <plan file>`: it stores the path, zeroes the round count and rewrites the pack from the plan's Files, Interfaces and Tasks, and exits 2 listing each token it cannot resolve.

Done when every section is filled under its own heading, every hit of the Files sweep is listed under Files or ruled out under Rulings, the Gate covers every package in Files, the Red commit is named when the workflow doc requires one, the size is estimated with any split it calls for, every ruling is tagged, each doc-governed or runtime ruling names the quoted rule or the code it rests on, and every known hazard is a ruling or an invariant, and, with a state file, `tkt-plan set` exits 0.

### 3. Verify

With a state file, run `tkt-plan <state> verify`: it runs the stale-plan check, `plan-check` and one Verifier round, saves the report to `<run>/<repo>-<issue>-verifier-out-r<n>.md` and counts the round. Line 1 of its stdout says what follows: `PLAN-OK` (done); `LINES n=` (the report's numbered lines, to fix or rule below); `STALE` or `PLAN-CHECK` (the round did not run; the digest lists what blocked it); `ROUND-LIMIT` (see Round limit). `tkt-plan <state> confirm --edits <file>` is the confirm round. The rules on who revises and on the round limit bind both paths; the checks and briefs below are what the command runs, and what you run without state.

Before each round, run `implement`'s stale-plan check, then `~/.agents/bin/plan-check <plan file> --base <BASE> --cwd <your worktree>`, with the `BASE` the Verifier brief takes. It reads the base through git, so run it from your own worktree and leave the shared checkout's HEAD where it is. Also compare each Files path with the fence the brief or ticket names: a path outside it is a grant request to the orchestrator, settled before the Verifier runs. Every line `plan-check` prints blocks the round. For each, add the path to Files, correct the path or symbol, or mark the line: `new` when the plan creates the name, `removed` when it deletes it, `reads` when the task only reads the path (a script the Gate runs, say) or it is a fixture, `example` when the token is sample data, not a name in the code (`c_history`). A `path:12,40` or `path:12-40` citation is lines of `path`. A round after a stale-plan revision verifies the revised tasks and doesn't count toward the round limit below. Fill `briefs/verifier.md` with `PLAN=<plan file's absolute path>`, `ISSUE`, `REPO` and `BASE` (it takes no `SPEC` or `WORKFLOW_DOC`) and an `EXTRA` that opens with the ticket: its body and its comments (`gh issue view <n>`, then `gh issue view <n> --comments`) written to a file and passed as `@<file>` or `tkt-plan verify --extra <file>`, because the Verifier's sandbox prints nothing for `gh issue view`. `EXTRA` also carries lines the Verifier needs verbatim, such as a repro command, an artifact path or a clock. Run the Verifier in a checkout of the base on a `strong` model from a different family than yours, or a `frontier` one when the plan's rung is `frontier`. A Verifier model the brief fixes (the owner's rule for the project) replaces the different-family rule, even when it shares the planner's family. Save its report to a file of its own (`~/.cache/agents/<repo>-<issue>-verifier-out.md`), never the filled brief's `--out` path, and open it before acting: it starts with `PLAN OK` or a numbered line. When a worker wrote the plan, its brief forbids delegating, so the session that started it runs the Verifier and hands each line back. For each line it returns, fix the plan or record a ruling. A line saying a ruling contradicts the ticket or a doc, or invents behaviour a person or a calling model sees where the doc is silent, is a `core` item: park the ticket at once, without a revision round. A line showing the plan departs from a ruling already posted on the ticket is a plan fix: follow the posted ruling. A line asking for a choice between designs is a ruling, not a revision, when the choice changes behaviour a person or a calling model sees, or contradicts or extends a doc. Record it under Rulings when the ticket, a doc or an earlier ruling on the ticket decides it; otherwise send the ticket to triage as below. The planner never picks one. A choice inside the implementation that no doc, person or calling model sees stays the planner's, stated with its reason in the plan. A core ruling still open parks the ticket (see `implement`).

**Who revises.** The planner writes the first draft at the plan's rung. A Verifier or `plan-check` line whose edit is fully specified (a wording or citation fix, an added Files path, a fixture or list entry, a `new`/`removed`/`reads` mark) is applied by a `standard` model, in a fresh session given the plan file and the lines; the planner's session, with all its reading in context, is too costly for a typo. Only a line that needs a design change returns to the planner, and a ticket (or part) gets one such design revision. A second means the contract is unsettled or the ticket too big: split it or send it to triage, as at the round limit below. A ruling that changes a signature, a type or the repro target is a design revision, whoever applies it. A design revision's report answers each Verifier line by its number. When the plan needs rulings, the first request lists every design line still unruled, so they arrive together.

**Round limit.** Unless the workflow doc sets its own limit, a plan gets two Verifier rounds, then at most one confirm round, then triage. Count every Verifier run as a round, whether you revised the plan in place or re-filled the brief; only a round after a stale-plan revision is exempt. Every answer is an edit the Verifier hasn't seen, so after round 1 re-fill the brief from the revised plan file and run round 2. After round 2, run a confirm round only when the finding behind every open round-2 line fully specifies its edit (a wording or citation fix, an added Files path, a fixture or list entry) and none needs a choice between options. A line whose edit you would have to work out yourself, not copy, is not a confirm edit: it goes to triage with the open lines. Make those edits, write each round-2 line with its edit to a file, and fill `briefs/confirm.md` with `PLAN=<plan file's absolute path>`, `EDITS=@<that file>`, `ISSUE`, `REPO` and `BASE`; run it on the Verifier's model. A plan that hasn't passed when its rounds run out, or whose round-2 lines need a choice, goes to triage: post the open lines on the ticket as questions (a line you answered after the last round the Verifier saw is still open), apply the label `docs/agents/triage-labels.md` maps to the `needs-triage` role, and stop. The ticket parks only when triage leaves a `core` item open. When triage answers every line, write each answer into Rulings and go on to step 4 without another Verifier round. A revision that applies a posted ruling is exempt from the design-revision limit, but the Verifier run that checks it counts as a round. A later part of a split takes implement's stale-plan check before its lane, like any plan.

Done when round 1, round 2 or the confirm round says `PLAN OK` on the plan as it will be posted, or, once the rounds run out, triage has answered every open line.

### 4. Post

Post the plan with `~/.agents/bin/post-plan <issue> <plan file> --repo <owner/name>`. It splits a plan over GitHub's comment limit at its `## ` headings into several comments, and prints one URL per part. When the plan changes, run it again: it edits its own comments in place (GitHub keeps their history), adds or deletes parts as the size needs. A section over the limit exits 1 and posts nothing: split that section. For one part of a split ticket, add `--part <label>` (e.g. `--part P3`): each part's plan then keeps its own comments, and a part never edits or deletes another's.

With a state file, `tkt-plan <state> post [--part <label>]` runs `plan-gate` and then `post-plan`: `POSTED urls=` is done, `POST-FAIL reason=gate` or `reason=post` carries the tool's message.

Done when `post-plan` exits 0 with the current plan.

### 5. Brief the lane

Fill `briefs/lane.md` with `PLAN=<plan file's absolute path>`, `ISSUE`, `REPO`, `WORKFLOW_DOC`, the base, worktree, branch, `GATE="$(~/.agents/bin/plan-gate <plan file>)"`, `ATTRIBUTION` (the attribution line your own instructions require in a PR body; the lane's instructions require none, and `ship-pr --body-has` fails without it) and `CLOSING`: `Resolves #<n>` for a PR that finishes the ticket, `Part of #<n>` for one part of a split. `EXTRA` (optional, empty by default) carries lines the brief must hold verbatim, such as the workflow doc's PR-body lines, a label for the PR or a testing rule the project's notes require. The slot is the brief's last line, so a sentence that must end the brief, such as a clock sentence, goes in `EXTRA` and nowhere else. The brief's stop limits are structural: they catch a change of scope, and a large change inside scope is review's to judge.

With a state file, `tkt-build` fills this brief from state and the plan's gate, so there is nothing to fill by hand.

Done when `fill-brief` exits 0.
