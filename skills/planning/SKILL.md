---
name: planning
description: "Write a ticket's implementation plan: a contract sketch (rulings, files, tasks, interfaces, review focus), with one advisory Verifier round only for `needs-plan` tickets. Use when planning a ticket or filling a preflight, planner, Verifier or lane brief."
---

The orchestrator writes every ticket's plan, after reading the code it describes: a lane fails on a plan describing code its author never read. The plan becomes the body of the lane's brief.

**Briefs.** The templates are `briefs/preflight.md`, `briefs/planner.md` (for a worker that writes the plan), `briefs/verifier.md`, `briefs/confirm.md` and `briefs/lane.md`. Fill them with `~/.agents/bin/fill-brief <template> KEY=VALUE...` (a value of `@<file>` reads the file), which fails on any unfilled placeholder or unknown key (a template's keys are its `__NAME__` placeholders), so the brief never goes out half-filled and you write only the values. When a filled brief starts another job, fill it with `--out <absolute path>` (e.g. `~/.cache/agents/<repo>-<issue>-<template>.md`: a durable directory, since a reboot clears `/tmp`; `fill-brief` creates it) and use the printed line verbatim as its prompt, never a hand-written path.

**Base.** Every brief takes `BASE`, the code the plan describes, which the orchestrator prepares (see `implement` step 2): `origin/main` for a new ticket, the PR's branch with `origin/main` merged in for a re-plan. Read, plan and verify against that base.

**Pack.** `plan-sweep` writes the ticket's context pack: symbol sites, file outlines, doc sections, and an Outside Files list of the paths its symbols reach that the plan's Files do not cover. `preflight.md`, `planner.md`, `verifier.md` and `confirm.md` take it as `PACK` (`none` when no sweep ran). With a state file, `tkt-start` writes it and `tkt-plan <state> set` rewrites it from the plan; by hand, `~/.agents/bin/plan-sweep --help` shows the call.

**Commands.** With a state file, steps 2 to 5 run through `tkt-plan` and `tkt-build`, started as `implement`'s Commands says; each step below names what its command does. Without state, the step's own text is the procedure.

### 1. Read

Start from the pack and read further code only where it points. Read every file the preflight listed and every file the plan will name. Line numbers in a ticket or brief are hints: anchor each citation by grep or heading at the base. Send bulk reading beyond that (history, issue archives, unrelated modules) to sub-agents that return summaries.

Read the ticket's body and then its comments (`gh issue view <n>`, then the same with `--comments`, which prints no body); a plan or scope comment outranks the body where they differ. Read every ruling posted on the ticket. A plan that touches a mechanism a posted ruling governs, a re-base re-plan included, quotes that ruling under Rulings and follows its words.

Search open issues for each identifier or path the acceptance or the plan's Files names (`gh issue list --state open --search '<construct>'`), and list each hit under Rulings in one line saying why it does or does not bear on this ticket: another ticket about the same construct is a dependency only its body reveals.

Done when you have read every file the preflight listed, every file the plan will cite and every ruling posted on the ticket, and searched open issues for each named construct.

### 2. Write the plan

A plan is a sketch of contracts and invariants, never code: a function body in a plan is the implementation done twice.

```
# Plan: #<n> <title>
<one-line goal>
Base: <full SHA of the base the plan was read against>

## Project constraints  pointers to the repo's standing rules (dependencies, budgets, code rules) where the workflow doc lists them; never copied
## Rules this ticket implements  each governing sentence from a doc, spec or ticket, quoted word for word with its file and section
## Rulings              each contradiction found and the default chosen, tagged core or non-blocking
## Files                the paths whose existing code the lane rewrites, at function or docs-section level, the files it creates, each with what changes, and any paths it only reads; this is the lane's fence, and tools read every path listed here as held. Mark a path the lane only reads with a trailing `(read)`; an entry without that marker is a write. Leave out an additive edit at a registration point (a new enum variant, match arm, struct field, `mod` line, slash-table entry or test function): the second PR to merge takes main and resolves it, and `tkt-gate` lets a pure-addition edit to an existing non-stop-list file pass. Include docs sections in Files, since `tkt-gate` stops unplanned docs edits with `STOP-LIST`. Sweep for it, ruling each hit in or out from its lines in the file, never from a summary: start from the pack's Outside Files list, then search the repo for every changed symbol, signature, type, listed value and behaviour, and list every caller, test, rules or lint file, doc and dependency manifest the change reaches: the tests and snapshots pinning output or a list the change shifts or extends, every exhaustive match on an enum gaining a variant (found by adding the variant in a scratch copy of the base and building every target, since a name search misses a match on a field of that type, such as `match failure.code`; list each file the build reports that needs more than an added arm; such a compiler cross-check bounds Files only when it applies the plan's full type change, every task's retype included, and one run on a subset gives a floor, which the plan names as a floor or replaces by running the full change), every use of a deleted or renamed type, every test file that calls a changed or removed name, the file a `#[path]`-declared test module lives in (the declaring file is not it), and the lockfile for a new dependency. A plan approves a new crate only when its name appears in backticks in Files or Tasks. A caller count in the plan quotes the search that produced it. Write each path in backticks, since `plan-check` and `tkt-gate` read only backticked tokens (a bare path fences nothing, so a non-additive change to it is reported as `OUTSIDE-PLAN` (the gate passes and records the paths in ticket state; ship checks that state's `outside_plan` list against the diff); a stop-list path refuses with `STOP-LIST`); a directory ending in `/` or a pattern holding `*` covers the paths under it. A Files path the base lacks takes the mark `(new)` on its line when the plan creates it, as in ``- `src/new_mod.rs` (new)``; tkt-drive passes each Files path marked `new` or `new-confirmed` to fence-grant as `--new`, and fence-grant refuses an unmarked missing path. The bare word `new` anywhere on a Files line outside backticks marks the path new, so describe an edit to an existing file with a verb such as `change` or `extend` (`plan-check` reports `drop the new mark` for an existing path the word marks). A path a task only reads, outside Files, takes `(reads)` on the task's line, as in ``1. Read `.config/nextest.toml` (reads) for the Gate``, because a read listed under Files holds that file against other lanes
## Tasks                in order; each: behaviour, test first, gate command, done-when. A task's gate command runs only that task's tests, because the lane brief bans crate-wide and workspace-wide test runs (such as `cargo nextest run -p main` or `-p main --bins --tests` with no filter), and a lane given one stops instead of running it
## Gate                 the lane's gate as one literal command line. When the workflow doc names a gate script (e.g. `scripts/check`), the line runs that script exactly as the doc writes it, with no name filter (environment assignments that only cap parallelism or caching, such as `CARGO_BUILD_JOBS=3 CARGO_INCREMENTAL=0`, may stand in front of it; one that filters tests or sets features, flags, a profile or a target directory may not), never its steps written out by hand, since a hand expansion drops the script's setup steps (a fixture build, a generated file); a pre-push check the doc lists apart from the script joins it with `&&`. For fiber, the gate is `scripts/check`, never one of its pieces such as `cargo xtask screen-ratchet`. Otherwise: format, lint and the full test suite of every package Files touches, each run through the runner the workflow doc names (e.g. `cargo nextest run`, not `cargo test`, when it names nextest); this line is the job-end gate, so it holds no name filter and no `--test <file>`. A `shellcheck` step names each library the script sources beside the script, as the project's gate does (`shellcheck scripts/release-size scripts/lib/release.sh`): run on the script alone, it reports the library's variables as never assigned (SC2154). A task's own gate command under Tasks selects that task's tests by where they live. For an integration-test file, use `--test <file>`. For unit tests inside the library, use `--lib` with a filterset on their module, as in `--lib -E 'test(/keeper_tests::/)'`. Never use a bare name filter with `--tests` or `--bins` (`-p main --bins --tests exit_alias` selects zero tests). Confirm with `cargo nextest list` and the same selector that it lists the task's new tests by name. A selector that matches other tests but not the task's own, such as `--test sandbox` for unit tests in `src/keeper_tests.rs`, passes over none of them. The line also holds the checks the workflow doc requires before a push; the section holds only that line, since `plan-gate` reads all of it: join the steps with `&&`, write `$(…)` for a substitution (`plan-gate` fails a backtick left after it strips the wrapping pair), and put a note on the gate under Rulings
## Fix gate             optional; one command line with `<since>`, which `tkt-fix` replaces with the pre-fix head SHA and runs as the fix job's job-end gate. Omit it when the repo's gate has no scoped mode (e.g. fiber); the merge gate, scoped verify and CI still run `## Gate`
## Red commit           when the workflow doc gates `bug` fixes on a commit that fails first: the test files that commit holds alone (they must build without the fix); otherwise `none`. When the ticket cites a failure location (a panic or assert at a file:line), the repro fails at that line: quote the line and its caller and name the test that fails there. A repro that fails elsewhere is a different bug; if none can fail at that line, say so and send the ticket to the triage role
## Interfaces           signatures, invariants, one literal example per line on the wire; no bodies. Each existing hook, seam or helper a task or test relies on, with its file, function and visibility (e.g. `pub(crate)`)
## Review Focus         where reviewers look: input classes and failure modes the tests may not cover
## Rung                 the lane's rung (per the `delegate` skill) and the reason
## Size                 estimated lines of code and lines of tests, separately; the split, if any
```

A plan whose ticket ends in measurements rather than a PR declares `Outcome: measurement` on the line after `Base:`; without that line the outcome is `pr`.

The quoted rules are what the Verifier, the reviews and any finding are judged against: a finding that contradicts a quoted rule is refuted by quoting it. A rule you can't quote from its doc is dropped, or asked of the triage role. A field or shape on an external wire cites its research file or probe output under Interfaces; one with neither is a `core` ruling. Check each ruling before the Verifier does: a ruling on behaviour a doc governs names the quoted rule it follows, and one that promises runtime behaviour cites the code at the base that runs it.

A known hazard is settled in the plan as a ruling or an invariant under Interfaces. On a `needs-plan` ticket, the advisory Verifier may challenge it; the lane keeps the settled contract. A hazard you can't rule on is a `core` ruling, and parks the ticket. So is a ruling that contradicts a ticket criterion or a doc sentence, or that invents behaviour a person or a calling model sees where the doc is silent: the ticket and the docs belong to the triage role, so such a ruling parks the ticket before the advisory round. A choice between two readings of a doc sentence is a `core` ruling too, never a `non-blocking` default. The plan carries every behaviour the ticket states: none is deferred to another ticket or part, and a ticket too big for one plan is split.

The rung is `standard` by default. It is `strong` when Interfaces or Review Focus involve state carried across calls, concurrency or timing, replay, or a quoted rule with several cases, and `frontier` for cross-cutting design.

Estimate tests from the testing rules the workflow doc states (every case, every listed sequence), never as a fraction of the code: plans have come in at half their merged size, mostly in tests. Count a built change's lines, sites and asserts against `git merge-base origin/main HEAD`, which leaves out main's newer commits. When the workflow doc's size rule calls for a split (past 1,800 lines of code plus tests only when the doc says nothing about size), split the ticket into parts from the start: each part a lane and PR of its own, in order, cut at a seam that leaves main green, `Part of #<n>` until the last, which is `Resolves #<n>`. A plan near GitHub's 65 KB comment limit means the ticket needs a split: triage adds Delivery parts to the ticket body, and each part gets its own plan.

A ticket that adds a ban (a lint, a disallowed method, a grep check) lands the ban in its first PR, with every existing site allowed by name, so no new site arrives while the migration runs; later PRs remove the allowances. A mechanical migration (one rewrite applied at every site, with no behaviour change) is one PR whatever its size: its review reads one rewrite, however many sites it touches.

Size each task as the smallest unit that carries its own test cycle. A regression test for a race names the mechanism that forces the interleaving (a pause point, barrier or held lock) and is checked to fail without the fix before dispatch; a test that only runs the path passes either way. A task that changes a threshold or adds a guard names the assertion that kills its obvious mutant: the value held at the boundary, both sides of it, or the exact error kind, never only "tests pass"; CI's mutation run catches the gap otherwise, one round late. Tasks run in order in one lane, under one `review-loop` for the PR. A migration may break the callers it lists under Rulings instead of paying for interim compatibility. A task that rewrites a literal across files names a script run on a scratch copy and checked by diff, or edits by hand. A script's check that a file contains X runs before the insertion it guards; after it, the check always passes.

A task with a wait, poll or retry carries a margin table: per wait, the margin is the bound minus the time of the event it waits for, in ms, computed from the code's constants (quote them) in one pass over every wait the change touches, so a Verifier round checks the table and finds no further row. A fake clock advanced on a "parked" state names the thread and the signal that the awaited state was recorded.

Defaults come from the project's catalogues first: an error code from the error doc, a name or format from the doc that lists it. A fence grant for a shared file names the line. A new file the change or its tests need (a test module, a fixture) is a Files entry too: the lane stops on any path the plan doesn't list. A type from another crate is written in the path form that resolves (`::tools::` when the crate has its own `mod tools`).

With a state file, record the plan with `tkt-plan <state> set <plan file>`: it stores the path, keeps the round count when the path is unchanged and zeroes it for a different path, and rewrites the pack from the plan's Files, Interfaces and Tasks, and exits 2 listing each token it cannot resolve. Start a re-plan with `tkt-plan <state> replan`: it clears the round, lane, fix and preflight slots with findings for a fresh plan round and keeps the verifier counts.

Done when every section is filled under its own heading, every hit of the Files sweep is listed under Files or ruled out under Rulings, the Gate covers every package in Files (for a gate script, by what the script runs), the Red commit is named when the workflow doc requires one and its repro fails at the failure line the ticket cites, the size is estimated with any split it calls for, every ruling is tagged, each doc-governed or runtime ruling names the quoted rule or the code it rests on, and every known hazard is a ruling or an invariant, and, with a state file, `tkt-plan set` exits 0.

### 3. Verify

Run this step only when the ticket has the `needs-plan` label. Otherwise, set the plan from the ticket with `tkt-plan <state> set <plan>` and go to step 4. Set and post default to no Verifier; `--no-verifier` remains accepted.

A plan with open design questions still stops at `QUESTIONS`; route slot or fence questions to flywheel and doc questions to surveyor, record the answer with `rule-questions`, then continue. This is separate from the advisory Verifier result.

For a `needs-plan` ticket, run `tkt-plan <state> verify` once after the plan is written. It checks the base and `plan-check`, then runs one advisory Verifier round and saves its report. `PLAN-OK` and `LINES` are both recorded; `LINES` does not block setting or posting the plan or dispatching the lane. Missing, stale or unconfirmed Verifier results do not lock `set` or `post`. Do not require a confirm round or run another Verifier round in this path. When the lane finds an open design choice, it adds `needs-plan` with a one-line reason and stops.

Before returning, the planner runs `~/.agents/bin/plan-check <plan file> --base <BASE> --cwd <worktree>` and clears every line by adding its path to Files, correcting it or marking it `new`/`new-confirmed`/`removed`/`reads`, returning only with a clean check or named lines it cannot mark without a ruling; `tkt-plan verify` resumes a recorded `job.planner` once with failing lines and reruns the check before spending a Verifier round, reports when no planner job is recorded, and stops with `PLAN-CHECK` when no job is recorded or the recheck still fails.

Before the advisory round, run `implement`'s stale-plan check and `~/.agents/bin/plan-check <plan file> --base <BASE> --cwd <your worktree>`. Resolve each `plan-check` line by adding its path to Files, correcting it or marking it `new`, `new-confirmed`, `removed` or `reads`; an unresolved check still stops with `PLAN-CHECK`. A path outside the plan fence is settled before the round. Fill `briefs/verifier.md` with the plan, issue, repo and base, and dispatch one round on the project's Verifier model (otherwise a `strong` model from another family, or `frontier` for a frontier plan). Read the report: `PLAN OK` or `LINES`; `LINES` is advisory and continues to post and lane dispatch.

Read advisory `LINES` findings and record any useful correction or ruling in the plan. They do not require a revision or another Verifier pass; a separate open design choice follows the `needs-plan` route above.


## Build and fix round limits

| Tool and verdict | Meaning | Next command |
| --- | --- | --- |
| `tkt-build ROUND-LIMIT` | `tkt-build` is the wrong phase after round one, not a spent review budget | continue with `tkt-fix <state> --verify` or `tkt-ship <state>` |
| `tkt-fix ROUND-LIMIT` | the round limit is reached; a fresh fix or any resume except a NEEDS_CONTEXT job needs a grant | resume a NEEDS_CONTEXT job without a grant; otherwise pass a ruling with `grants: round <next round>` through `--ruling` before another fix round |
| `tkt-plan verify QUESTIONS` | the plan lists unanswered design or acceptance choices | record the answer with `tkt-plan <state> rule-questions --comment <id>`, then run the one advisory round |


Done when the plan passes `plan-check` and `plan-gate`, and, on a `needs-plan` ticket, the one advisory Verifier round has returned `PLAN-OK` or `LINES`.

### 4. Post

Post the plan with `~/.agents/bin/post-plan <issue> <plan file> --repo <owner/name>`. It splits a plan over GitHub's comment limit at its `## ` headings into several comments, and prints one URL per part. It runs `plan-gate` first and posts nothing when the plan's `## Gate` is missing or invalid. A section over the limit exits 1 and posts nothing: split that section. For one part of a split ticket, add `--part <label>` (e.g. `--part P3`): each part's plan then keeps its own comments, and a part never edits or deletes another's. With a state file, `tkt-plan <state> post` supplies a run ID stored in that state. It edits only that run's comments in place, adding or deleting parts as needed. `tkt-start` begins a new run ID.

With a state file, `tkt-plan <state> post [--part <label>]` runs `plan-gate` and then `post-plan`: `POSTED urls=` is done, and `POST-FAIL reason=gate` or `reason=post` carries the tool's message. A missing, stale or `LINES` Verifier result is recorded as `skipped` and does not lock post or lane dispatch. A `POST-FAIL reason=verdict` retains the separate route for a non-Verifier plan stop such as `QUESTIONS`.

Done when `post-plan` exits 0 with the current plan.

### 5. Brief the lane

Fill `briefs/lane.md` with `PLAN=<plan file's absolute path>`, `ISSUE`, `REPO`, `WORKFLOW_DOC`, the base, worktree, branch, `GATE="$(~/.agents/bin/plan-gate <plan file>)"`, `LANE_MODEL` (the lane slot's model id), `CLAIM_HOLDER` (derived with `claim_holder "$ISSUE"` from `~/.agents/bin/lib/lane-ticket.sh`; tkt-job derives it for state-backed fills), and `CLOSING` as the intended closure record: `Resolves #<n>` for a PR that finishes the ticket, `Part of #<n>` for one part of a split. `EXTRA` (optional, empty by default) carries testing rules, labels or other brief instructions, never PR-description requirements. The slot is the brief's last line, so a sentence that must end the brief, such as a clock sentence, goes in `EXTRA` and nowhere else. The brief's stop limits are structural: they catch a change of scope, and a large change inside scope is review's to judge.

With a state file, `tkt-build` fills this brief from state and the plan's gate, so there is nothing to fill by hand.

Done when `fill-brief` exits 0.
